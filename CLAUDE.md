# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

«Вотэс» — a Duolingo-style game for children learning the Udmurt language, built for the
«Удмуртский ИТ-класс „Вотэс“» hackathon (mobile track). All UI text, comments, commit messages and
docs are in **Russian**; keep it that way. Deadlines and the feature roadmap are in `ROADMAP.md`;
judging criteria that drive priorities are summarized there.

Architecture in one line: a **server-rendered Django app** (HTMX + Alpine.js + Tailwind) is the whole
game; the **Flutter app in `mobile/` is only a WebView wrapper** around it. Game logic never lives in Dart.

## Commands

All tooling goes through **mise** (mandatory; see `LOCAL_SETUP.md`). Configs are split so each part
installs only what it needs: `backend/mise.toml` (uv, Tailwind CLI; uv installs Python 3.12 per `backend/.python-version` and the deps into `backend/.venv`),
`mobile/mise.toml` (Flutter 3.47, Java 17), root `mise.toml` (Docker tasks only). Never use the system
Python/pip; run commands via `mise run <task>` or `mise exec -- uv run <cmd>` from the relevant directory.
Dependencies live in `backend/pyproject.toml` + `backend/uv.lock` (change them with `uv add`/`uv remove`,
commit both); there are no `requirements*.txt`.

Backend (run from `backend/`):

```bash
mise install && mise run setup                          # uv sync, migrate, seed (seed only adds what is missing)
mise run dev                                            # runserver 0.0.0.0:8000
mise run test                                           # pytest (settings in pyproject.toml)
mise run test -- tests/test_answer_check.py::test_check_answer   # single test
mise run lint                                           # ruff check + format --check + migrations check (as CI)
mise run fmt | css | seed                               # format / rebuild app.css / reload course (--reset)
```

Without `DATABASE_URL` the app uses SQLite; without `USE_S3=1` media goes to `backend/media/`.

Full stack: `mise run up` (= `docker compose up --build`) from the repo root (web on :8000, MinIO console on :9001,
admin `admin`/`admin12345`). `backend/entrypoint.sh` runs `migrate`, `seed` and `createsuperuser` on every start.
`backend/Dockerfile` is `python:3.12-slim` + the uv binary; it runs `uv sync --locked --no-dev` and puts
`/app/.venv/bin` on `PATH`, so the image and local dev use the same locked dependencies.

CSS: `backend/static/css/app.css` is **compiled and committed**. After adding Tailwind classes to
templates, rebuild it with `mise run css` (standalone Tailwind CLI v3.4.17, no Node; it scans only
`backend/templates/`). Classes not present in the compiled CSS silently do nothing.

Mobile (`cd mobile && mise run setup | check | dev | apk | apk:ask`; Android SDK comes from Android Studio,
not mise; CI builds the APK): only `lib/`, `test/`, `assets/`, `pubspec.yaml` and
`android/app/src/main/AndroidManifest.xml` are committed — the rest of `android/` is generated by
`flutter create --platforms=android --org ru.votes .` (`mise run setup`). The launcher icon is
`mobile/assets/icon/*.png` (rendered from the `.svg` next to them); `dart run flutter_launcher_icons`
(in `mise run setup` and in CI) writes it over the default Flutter icon. Keep `mobile/test/widget_test.dart` in the repo:
otherwise `flutter create` generates a default test referencing `MyApp` and `flutter analyze` fails.

## CI/CD (`.github/workflows/`)

`ci.yml` runs on every push and PR (via `uv sync --locked`): ruff, migrations check, pytest. `android.yml` runs only when
`mobile/**` or the workflow itself changes (plus manual `workflow_dispatch`): `flutter analyze`,
`flutter build apk`; on `main` its `release` job publishes a GitHub Release `apk-<run_number>` with
`votes.apk`. Backend-only changes don't produce a new APK. The stable download link is
`releases/latest/download/votes.apk`. The server URL baked into the APK is
`vars.SERVER_URL || https://hakaton.marshmeg.ru` (also the Dart default in `mobile/lib/main.dart`).
The same job also builds `votes-ask.apk` with `--dart-define=ASK_SERVER_URL=true`: that build shows the
server-address screen on every launch (for testing against another server); both APKs go into the release.

Deploy: the `deploy` job in `ci.yml` (push to `main`, after `backend` passes) rsyncs the sources to
`/opt/votes` on the server (`vars.DEPLOY_USER@vars.DEPLOY_HOST`, key in `secrets.DEPLOY_SSH_KEY`) and runs
`docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build`, then curls
`vars.DEPLOY_URL`. `docker-compose.prod.yml` adds Caddy (`deploy/Caddyfile`: HTTPS, `/votes-media/*` → MinIO)
and unpublishes the web/MinIO ports. The server's `/opt/votes/.env` (secrets, `SITE_ADDRESS`,
`S3_PUBLIC_*`) is not in git and is excluded from rsync. The prod overlay sets `DJANGO_HTTPS_ONLY=1`
(Secure cookies + HSTS). `minio-init` (every `up`) sets a bucket policy with anonymous `s3:GetObject`
only — listing the bucket is forbidden. The MinIO image is `pgsty/minio` — the official
`minio/minio` was removed from the registries.

## Backend architecture

Three Django apps under `backend/`:

- `courses` — content only: `Course → Unit → Lesson → Exercise`, edited via Django Admin or loaded
  from `seeds/content.yaml` by `courses/management/commands/seed.py`. Plain `seed` (run on every
  container start) only adds units/lessons missing by title and never rewrites an existing lesson —
  player results reference lessons; `seed --reset` deletes the course together with those results. `Exercise.kind` is one of
  `choice | type | assemble | match`, and the meaning of `answer`/`options` depends on the kind
  (documented on the model and at the top of `content.yaml`). Multiple accepted answers are separated by `|`.
- `learning` — playing a lesson.
  - `services/lesson_engine.py` holds the lesson run **in the Django session** (`lesson_run`: queue
    of exercise ids, position, hearts, xp, mistakes, `answered` flag). Wrong answers cost a heart and
    re-queue the exercise once; XP is only for first-try correct answers; `finish()` writes
    `LessonResult` and calls `Profile.register_activity()` (XP + streak). Replaying an already
    completed lesson gives half the XP. Wrong pairs in `match` cost no heart but count as mistakes.
  - `services/progress.py` — which lessons are done/open (a lesson opens when the previous one in
    course order is done). Used by `home` and by `open_lesson_required` on every lesson view, so a
    locked lesson can't be started by a direct link.
  - `services/answer_check.py` — answer normalization and the Udmurt-specific verdict: the five
    extra letters **Ӝ Ӟ Ӥ Ӧ Ӵ** typed as plain Cyrillic (ж з и о ч) give `ALMOST`, not `WRONG`.
  - `views.py` — HTMX flow: `lesson_answer` (POST) and `lesson_next` (GET) both re-render
    `templates/learning/partials/lesson_body.html` into `#lesson-body`; finishing returns an
    `HX-Redirect` to the result page. Non-HTMX requests fall back to full pages/redirects.
    Option order is shuffled with a seed of `(exercise.id, pos)` so it doesn't change after answering.
    `leaderboard` — top 50 non-guest profiles with XP, ordered by XP (equal XP shares a place); the
    current player is highlighted, or shown separately when outside the top.
- `accounts` — `Profile` (xp, streak, `is_guest`). The login page is the first screen: every game view
  is `@login_required`, and an authenticated player is redirected from login straight to the course map.
  After signup the player sees the one-time rules screen `learning:welcome`. There is no play without registration any more; `is_guest` only marks accounts left from the old
  guest mode. Signup creates a new user, or converts such a legacy guest in place (renames + sets
  password) so progress is kept. `get_player()` only ensures the profile exists. Login is by `username`;
  the player's name and family are `User.first_name`/`last_name` (asked at signup) and are only for
  display: `Profile.display_name` gives «Айно К.» and falls back to the username. The avatar in the header links to the profile page
  (`accounts:profile`: stats, recent `LessonResult`s, the logout POST form).
  `accounts:profile_edit` (`ProfileForm`) edits name, family, username and the avatar: the upload is
  re-encoded with Pillow to a 256×256 JPEG and stored in `Profile.avatar` (default storage, `avatars/`).
  In the APK the file chooser for that `<input type="file">` is wired in `mobile/lib/main.dart`
  (`setOnShowFileSelector` + `image_picker`) — Android WebView does not open one by itself.
  `accounts:password_change` is Django's `PasswordChangeView`; the minimum password length (6) is set in
  `AUTH_PASSWORD_VALIDATORS` to match `SignupForm`.

Templates: each exercise kind has its own partial in `templates/learning/partials/exercises/`;
client-side interaction (tile assembly, pair matching, the on-screen Udmurt letter keyboard) is
Alpine.js inline in those partials. `match` is checked on the client as the player goes and then submits the pairs as JSON
(`answer=[[udm, rus], ...]`, plus the client-side wrong-pair count in `mistakes`); the server compares
the pairs with `exercise.options`. An empty answer is not checked and costs no heart. Adding a new exercise kind means: a `Kind` choice, handling
in `lesson_engine.submit`, a partial, and a branch in `lesson_body.html`.

Game balance (hearts, XP) is in `settings.GAME`. Brand colors/fonts are tokens in
`backend/tailwind.config.js` (mirrored as constants in `mobile/lib/main.dart`). Fonts, htmx and Alpine
are vendored in `backend/static/` (no CDNs — the font must contain the Udmurt letters).

Media uses `django-storages` S3 backend against MinIO when `USE_S3=1`; public URLs come from
`S3_PUBLIC_DOMAIN`/`S3_PUBLIC_PROTOCOL` (behind HTTPS, `/votes-media/` must be proxied to MinIO).

## Content caveat

Every unit from «Цвета вокруг» onwards was added without native-speaker review.
The seed vocabulary is demo content and must be verified by a native speaker before submission
("контент соответствует действительности" is a judging criterion). Don't invent new Udmurt words
or phrases without flagging them as unverified.
